## 5. Every difference, and its cause

**Design record (`design_pusher.json`), 322 fields compared:**

1. `performance.service_ceiling_ft`: 31,738.2 ft at Gate B, 30,438.5 ft in r0 (-1,299.7 ft). Cause: the Gate B table ended at 30,000 ft and the lookup held the 30,000 ft power constant above it, so the old value was read with too much power. The extended table keeps falling. This is the one field the spec expects to change (ruling B-9c).
2. `performance.engine_table_top_ft` = 35000.0: added, not changed. The Gate B record was written before commit `5bb3f81` stored this field (Gate B report 4.7); the code that writes it is unchanged here.
3. `performance.service_ceiling_above_table_top` = false: added, not changed. The Gate B record was written before commit `5bb3f81` stored this field (Gate B report 4.7); the code that writes it is unchanged here.
4. No other field differs: the largest relative difference over the 322 compared fields is 0.

**Other files of the record:**

- `m250_table.json`: two more altitude rows (section 3); cells at or below 30,000 ft identical.
- `ledger.yaml`: values equal (111 values: yes; 55 bands: yes). The text differs in one entry: `prop_real_to_ideal` is labelled `assumed` since ruling B-10b (it was `published`); value and band are unchanged.
- `robust_candidate.json`: the same row of the re-size (`runs/task12/stage3/2026-11-26/m250_bands_resize`).

## 10. Assumptions made where the spec left a choice

Each stands until the owner changes it (spec section 2).

1. **No new sizing bisection.** The spec says to re-run the design at the record's L_sized. r0 keeps L_sized 11 h; the info-gap study then shows whether the Gate B horizons still hold (section 8). Reason: the extension changes no input of the sizing.
2. **Two rows added, at 32,500 and 35,000 ft**, on the table's existing 2,500 ft spacing. Reason: every existing row is kept and the interpolation error half way between the new rows is of the size it has between two old rows (section 3.2).
3. **The TP100 table is not extended.** Reason: it is not the chosen engine, and its records keep the table they were made with.
4. **Row 2 compares the fields both records have.** The two B-9c fields exist only in r0 and are listed as additions (section 5). Reason: they were added to the code after the Gate B record was written; calling them differences would stop the package on a field the ruling asked for.
5. **Row 3 is judged on the stored flag, and the two bisection probes above 35,000 ft are left in place** and shown not to affect the result (section 6). Reason: lowering the bisection's 60,000 ft starting bracket would move its midpoints, and with them the last digits of every ceiling the code computes, for a read that cannot change the answer.
6. **Row 4 needs both ends of the engine-cycle band inside ±1,000 ft**, and the band is read from the Gate B engine record, not recomputed. The same bisection with the table's own member was run as well (section 6).
7. **The integrated climb is the energy method in steps, ending at Stage 1's top-of-climb speed**, so that it covers the same energy change as the two-point estimate; the height-only figure is given next to it. Weight is held over each 1,000 ft step. Row 5 uses an upper bound on the mission-fuel change instead of flying the later legs again. Reason: the bound is 9 times below the threshold, so the finer answer cannot change the verdict.
8. **"The same ledger" means the same values and bands.** The current ledger differs from the Gate B copy in one label (B-10b).
9. **2 processes for the info-gap study**, as at Gate B, so that the process count is not a variable in row 6.
10. **Record layout:** `runs/task12/pd/2026-11-27/p0/r0/` holds the baseline with the Gate B file names, so the existing tools read it; `runs/task12/pd/2026-11-27/p0/p0.json` holds the checks. Later packages read `r0/`.
