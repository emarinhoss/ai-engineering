## Slide 1: Title

*0:00, 0.5 min*

I made a pipeline that sends design questions to a CFD solver and brings the answers back. A person does not do the routine steps. The pipeline does not give a result that it cannot check.

I show it on one small electric aircraft, from start to end. The status line at the bottom comes from the records.

## Slide 2: The problem, and why it needs a pipeline

*0:30, 1.5 min*

This is the problem. The aircraft carries a payload of 0.5 kg. The C2 class of the EASA open category limits the take-off mass to 4 kg. We want the longest endurance in that limit.

Six inputs define the design: span, aspect ratio, taper, battery fraction, camber and thickness. A graded ledger of 46 quantities fixes all other values.

Design work is a loop: propose, simulate, check, decide. The simulation takes the most time. One SU2 angle takes a median of 11.8 minutes on the coarse mesh, and a design needs five angles.

Each case also needs a mesh, a configuration and a check. A person usually writes these by hand.

The third problem is the worst. A solver can stop correctly and still give incorrect numbers. Slide 3 shows an example.

Thus the loop must run without a person, and it must check each result before a person sees it.

## Slide 3: A clean exit is not a correct result

*2:00, 1 min*

This is the design principle of the pipeline, so I show it early.

The first SU2 airfoil case stopped with exit code 0. It used all of its 3,000 iterations and wrote all of its files. The solver reported success.

But we compared it with a rerun that stopped correctly. The lift error was -10.5 %. The drag error was +24.7 %.

Follow the chain on the right. The drift rule read the history. Lift still moved 5.6 % and drag moved 17.4 % in the last fifth of the run.

The ruling set a budget of 6,000 iterations with a Cauchy stop. The rerun stopped at iteration 4,867.

Thus the pipeline does not trust the exit code. It decides convergence from the history.

## Slide 6: The pipeline at a glance

*4:30, 1.5 min*

This drawing shows the full pipeline. Read it from left to right.

The agent does not touch the solver. It calls typed tools. Each request goes through the gates first. A design that fails a gate stops here, with a message.

A request that passes becomes a job file in a shared queue. Cloud workers take the jobs from the queue.

A result does not go directly into the study. Checks after the run decide if it converged. Then a hash goes with it into a run record.

The surrogate learns from the records. An acquisition function selects the next batch. The language model never selects a design point.

A person must act at two marked points only: a ruling on the data, and a sign-in for a cloud runtime.

## Slide 7: The agent's interface: typed tools, not free text

*6:00, 1 min*

The agent gets to the solver only through 11 typed tools. Each tool has a strict schema.

The left column lists the tools. They stage, submit, ingest and report. They never run the solver.

A typed interface lets an agent operate engineering software safely. The tool rejects a request with an unknown field or an incorrect type. It gives a message and stages nothing.

Each call writes a line to an audit log.

The right column shows what does not depend on this interface. The worker does the physics gates again. It checks the mesh fingerprint and the configuration hash again.

The design points come from design tables and acquisition code, never from the language model.

## Slide 8: Gates before any solver

*7:00, 1 min*

A design must pass 5 gates before a solver runs.

Read the table from top to bottom. Gate 1 checks the cruise Reynolds number. Gate 2 checks the stall margin. Gate 3 closes the mass. Gate 4 checks the manufacturing floor, which is a study rule, and the wing loading. Gate 5 checks the quality of the lattice.

An airfoil case also passes a mesh-quality gate.

The gates are fast functions. In the low-fidelity grid, the gates stopped 72,009 of 531,441 designs.

Each refusal gives the value that caused it. A gated design costs no solver time.

## Slide 14: How each strategy picks the next design

*13:30, 1.5 min*

Two Gaussian processes make the surrogate. One models endurance. The other models the logarithm of take-off mass.

Each process gives a mean and an interval at each design in the box. Five strategies use them in different ways.

Random selects a design that has not run yet. The Latin hypercube spreads the full budget over the range of each input. These two use no model. They are the baselines.

Maximum variance runs the design where the model is least sure. It does not ask if the design is good.

Expected hypervolume improvement draws 128 samples at each candidate. It measures how much each sample increases the area of the current front. Good designs and uncertain designs both get a high score.

The last strategy multiplies that score by the probability to pass the gates. Slide 17 shows why we need it.

The language model calls tools. It never selects a point.

## Slide 15: Why a Gaussian process, and against what

*15:00, 1.5 min*

Why a Gaussian process? There are four reasons, and each comes from how the study uses the model.

First, the SU2 data are small. We have 32 SU2 designs. An exact Gaussian process fits this quantity in seconds.

Second, the acquisition and the confirmation test need an interval, not only a mean. A Gaussian process gives an interval at each design.

Third, each process has nine numbers: six length scales, two variances and a mean. The marginal likelihood sets them. Nobody tunes them by hand.

Fourth, the length scales show which inputs are important. Backup slide 40 shows them.

The table shows each model that we fitted on this data. The low model alone has an endurance error of 2.299 hours.

With 8 SU2 designs, the Gaussian process on SU2 alone has an error of 1.525 hours. The two-level model has 0.824 hours.

At 24 designs, the order changes: 0.704 hours for SU2 alone and 0.726 for the two-level model.

We did not fit a neural network or a tree model on this data. This table is the full comparison in the record.

The intervals cover less than 90 % of the held-out designs. Thus I use the mean, not the interval.

## Slide 17: Active learning on the open box, honestly

*17:30, 1.5 min*

This is the result that I show first, because it includes a loss.

On the open box, the full space with its gates, plain EHVI is worse than random. At 40 evaluations its regret is 0.317. Random has 0.294.

The reason is in the column of gated picks. EHVI selected a mean of 29.7 designs that the gates rejected. Random selected 1.9.

The front is near the gated edge, and the Gaussian processes do not know the gates. Thus EHVI goes to the edge again and again.

## Slide 31: Mass closure and the endurance balance

Two parts give the endurance number.

The first part is the mass closure. The battery mass is the battery fraction times the take-off mass. Thus the mass sum depends on itself. We solve it as a fixed point.

The second part is the energy balance. The usable battery energy, less the climb energy, divided by the cruise power, gives the endurance.

The nominal design closes in 18 iterations, at 6.75 hours.

## Slide 33: Two stopping rules: Cauchy stop and drift

How do we know that a run converged? We use two rules, and they measure different things.

The SU2 Cauchy stop examines lift and drag over a window of iterations, from iteration 500.

The first smoke case drifted 5.6 % in lift and 17.4 % in drag. The rerun stopped at iteration 4,867.

A run that stops at its budget gets a flag.

## Slide 41: Hypervolume regret: what the replay slides measure

Regret measures how much of the true front a strategy has not found.

Hypervolume is the area between a front and a reference point. The reference point is a little beyond the worst design. We measure endurance and the logarithm of mass.

The figure shows the true front of the pool and its hypervolume, shaded.

Regret is the true hypervolume, less the hypervolume of the designs found, divided by the true hypervolume. It is 1 when the strategy has found nothing of the front. It is 0 when it has found all of it.

The table gives the mean regret for each strategy and budget. For example, at 16 evaluations EHVI has 0.034 and random has 0.210.

## Slide 44: Queue, workers and shards

The queue is a shared folder of job files with status flags. Cloud machines cannot accept inbound connections. Thus the workers read the folder at intervals.

Each worker takes only the cases whose identifier hash is in its own shard. Each case is in exactly one shard. The 172 pool cases divided into 85 and 87 over two shards.

Thus two workers never take the same case, and there is no lock.

Each worker writes a heartbeat. When a worker stops, its heartbeat gets old, and the case runs again.

To add a worker, change the number of shards. Nothing else changes.
